# Frontend (Next.js)

Next.js 16 (App Router, Turbopack) with TypeScript, Tailwind v4, and shadcn/ui, managed with **bun**. It is a UI client only: no secrets, no LLM calls, no database access.

## Backend proxy

`app/api/[...path]/route.ts` forwards every `/api/*` request to `${DJANGO_API_ORIGIN}/api/*`. It is a route handler, not a `next.config` rewrite, so it controls the forwarded headers: it passes the visitor's address in `X-Forwarded-For`, which the API's rate limits key on. (A rewrite forwards the Next.js server's own address, which put every visitor in one rate-limit bucket.) Request bodies are buffered, because a streamed body arrives at Django empty. Response bodies are streamed, so Server-Sent Events work.

Django API routes have **no trailing slash** (`/api/lessons`, not `/api/lessons/`). Next.js normalises trailing slashes with a redirect, and Django's `APPEND_SLASH` would redirect back, which would create a loop through the proxy.

Swagger UI and the admin are served by Django on its own origin (`NEXT_PUBLIC_BACKEND_URL`), because they load Django's static files. No public page links to them.

This gives same-origin cookies and needs no CORS configuration. `EventSource` works as-is.

After sign-in, `/auth?next=…` only redirects to a path on this site (`RedirectPolicy.safeNext` in `lib/safe-redirect.ts`). Anything else, such as `//evil.com` or `/\evil.com`, falls back to `/`.

`proxy.ts` (Next 16 renamed `middleware.ts` to `proxy.ts`; it runs on the Node.js runtime) is a thin hook: it reads the `lc_session`, `lc_onboarded` and `lc_setting_up` cookies and asks `RouteGuard.redirectFor` (`lib/route-guard.ts`). `/` is the landing page for everyone (no redirect). `/auth` and the pages under it (`/auth/verify`) are for signed-out visitors: with `lc_session` it goes to `?next=` when it is a safe path on this site (`RedirectPolicy.safeNext`), else `/lessons`, or through `/onboarding` without `lc_onboarded`. `/onboarding`, `/profile`, `/lessons/*`, `/wallet/*`, `/streak/*` and `/buy/*` need the marker: without it they redirect to `/auth?next=…`, and without `lc_onboarded` to `/onboarding?next=…`, so the page they wanted is kept. An onboarded visitor has nothing to set up and is sent on from `/onboarding`, except in the last step: the profile is saved at step 4, which makes them onboarded, so the page sets the `lc_setting_up` cookie (`SetupMarker`) then and clears it when the setup ends, and a refresh on step 5 stays there with the landing page's topic still offered. The API still authorises every request.

The markers are httpOnly, so the page cannot read them. `GET /api/session` (`app/api/session/route.ts`, `SessionProbe`) says whether `lc_session` is there; `AuthProvider` asks it before `/auth/me`, so a signed-out visitor's console stays free of 401s. Loading and error states: `app/loading.tsx`, `app/lessons/loading.tsx`, `app/lessons/[id]/loading.tsx`, `app/error.tsx` and `app/global-error.tsx` (the root layout itself failed), and the console's own `loading.tsx` and `error.tsx` (the sidebar stays).

## The landing page

`/` is built from `docs/design/mockups/landing-page-mockup.html` (a design reference, rebuilt with the app's own tokens, fonts and components, not copied), with the root header hidden (`SiteHeader` returns nothing on `/`) in favour of its own public header: logo, the anchors `#how`, `#features`, `#pricing` and `#faq`, the theme toggle, and "Sign in" and "Start free" (teal). Someone who is signed in sees "Go to my lessons" instead: `RouteGuard` no longer redirects `/`, and the header reads the session marker cookie (`lc_session`) on the server, so there is no flash. `app/page.tsx` is a server component: it reads `GET /api/public/testimonials` and `GET /api/public/pricing` for every load (`cache: "no-store"`, forwarding the visitor's address so the API's limit is theirs), so the whole page is in the HTML the server sends. The client islands are the sample Quick check and the final band's topic form (it needs `sessionStorage` and the router). If either endpoint cannot be read the page still loads: the maker's note instead of quotes, and no number at all in the pricing (a plain line says prices are not available).

**Every number a visitor sees comes from the API** (`/api/public/pricing`: plans, credits, "about N full lessons", free credits, daily and streak bonuses, cost ranges, how long credits last, how many questions a Quick check asks), never from code, so a price edited in the console changes the page on its next load. The static words are in `lib/landing-content.ts`; components in `components/landing/` are thin and the rules are classes in `lib/landing/` (all with `bun test`):

## `/lessons/[id]`: the stage-driven view

Every state has the same header (`LessonHeader`): breadcrumb (My lessons / topic), title, a small tag (level, else route), and the `JourneyStepper` (on a phone only the current step keeps its label). Once the lesson is `ready` the tabs of `LessonTabs` sit under the stepper (`LessonTabBar`, the open tab in `?tab=`): **Lesson**, **Test** (badge "To do", "Getting ready…", "In progress", then "70% · attempt 2"), **Study sheets** (any ready lesson can have sheets made for it) and **Quick check answers**; a lesson that is only study sheets (`sheets_only`: it asked for them, or chose them after a perfect quick check) has just **Study sheets** and **Quick check answers**, no lesson and no test. The Study sheets tab is the sheet tab row: a chunky tab for each sheet the lesson has, a dashed "Add cheat sheet" / "Add revision sheet" for each it lacks, "Add both sheets" when it has neither (one request), and the PDF; while sheets are written their tabs are the building screen, and a request for a sheet that exists (a page that was out of date) just opens it. A lesson the learner rated themselves into has no **Quick check answers** tab: it had no quick check. The Test tab is the `AttemptRunner` deck, the "Getting your questions ready" state of a retake (with a **Cancel** that stops the run through `POST /runs/{id}/cancel`; the waiting attempt goes with it and nothing is used), or the result with its history.

**Follow-ups.** A graded result with an offer shows it twice: a `FollowupDialog` opens over a result that was just handed in (title, one message, **Not now**, and the one button the server chose: "Make a Foundation lesson", "Make an Advanced lesson" or "Open it"), and a `FollowupOfferCard` stays under the score with the same words and button, also when the result is looked at later from the history. A learner who rated themselves low and failed gets only that card, as a note with no button ("That one was a stretch…"). Pressing a button goes to the new lesson, or to the one that exists. The lesson header (`LessonHeader`) lists **Related lessons**: "Made from: <title>" on a follow-up, and "Foundation lesson: …" / "Advanced lesson: …" on the lesson they came from. The lesson list says "Foundation follow-up" or "Advanced follow-up" on a follow-up's kind line, and "Getting your lesson started" for a lesson that has no quick check to prepare.

**New lesson** (`/lessons/new`): the topic, then "How should we find your level?" as two pressable radio cards, **Take a quick check** (the default) and **Rate yourself**. Choosing the second shows the `StarRating`: five stars, each two halves, one radio group (Tab lands on it once; arrows, Home and End move the pick). The sentence for the pick appears under the stars and is read out as it changes (`aria-live`), and the button ("Start my lesson") stays off until a value is picked. The steps under the form change with the choice ("Your rating, Your lesson" has no quiz in it). Above the level question is **What would you like?** as two radio cards, **A lesson** (the default) and **Study sheets**; choosing sheets shows **Which sheets?** as three more (**Both**, picked at first, **Cheat sheet**, **Revision sheet**), and the words change with the pair (a rating with sheets: "Make my two sheets"). All three questions are `ChoiceCards`. A lesson that asked for sheets has its own short journey (Diagnose or Rate yourself, Your level, Study), its list pill says "N sheets ready", and its building screen ends with the sheets' steps.

The page loads `GET /lessons/{id}`, subscribes to the active run's events, and renders by `stage`:

| stage | Component |
|---|---|
| `preparing_diagnostic`, `generating_material`, `generating_lesson` | The building screen: `PipelineProgress` (eyebrow, headline, percent and bar, timeline with per-step time, a calm note when a step needed a second try, collapsed "Small notes", **Stop building** behind a `ConfirmDialog`) beside `StartingPointCard` (once the assessment exists; stacked on a phone). `loading.tsx` shows its skeleton. |

### `FlashcardDeck`, `QuickCheck` and `AttemptRunner`

`FlashcardDeck` shows one card at a time over two ghost cards that thin out as fewer questions remain, a segmented progress bar and "n / total". **There is no way back**: Continue is disabled until the card is answered, a lock hint says so, and the answer locks when the learner continues. The answered card flies off to the left and the next rises from the stack (~450 ms; instantly for `prefers-reduced-motion`). Keys: 1–4 / A–D pick options (D is "I don't know" in the quick check), Enter continues (not in a textarea). Answers are kept in memory and in `sessionStorage` (`deck:<lesson>:<kind>`), sent in one request at the end, and forgotten after a successful send.

- **`QuickCheck`** (diagnostic and prerequisite): a difficulty bar and band name, the question, four options keyed 1–4 and a dashed "I don't know this yet (D)". After the last card a "Quick check done!" card flips in ("Working out your starting point…") while the flow resumes; a failed send keeps the answers and offers "Send my answers". `409 already_attempted` hands over to the read-only answers.
- **The Test tab** (`TestTabPanel`) shows whatever the server says the test is, as a small state machine: a short **intro** with "Start the test" (no attempt yet; it explains that the learner answers one question at a time, can't go back, sees the score at once and can try again with new questions); **"Getting your questions ready"** while a retake is written (`AttemptPreparation` follows the `question_bank` run, and a run that fails or is stopped leaves no attempt, which reads as "try again": nothing is lost); the **`AttemptRunner`**; or the **result** of an attempt with the history. A refresh lands in the same place: an open attempt resumes on the first card without a saved answer, a retake that was still being written is followed again.
- **`AttemptRunner`** (`GET /lessons/{id}/test` for the open attempt, `POST …/test/attempts` to start): "Test · Show what you learned" with an "Attempt n" chip; multiple choice (A–D), choose all that apply, number (with unit), short answer, written answer and code. **Continue saves the answer on the server and locks the question there** (`AnswerLocker`, `PUT …/answers/{qid}`; an answer the server already has counts as saved, a failure keeps the learner on the card with a message), so a refresh or another tab cannot go back. The deck starts from the server's answers (`useAttemptDeck`, nothing in `sessionStorage`). The last button is marigold "Finish and hand in" and opens "Hand in your test?" (Not yet / Hand it in), then the last answer goes with `POST …/submit`; a lesson attempt comes back graded, so the result shows at once (an older lesson's written answers show "Marking your test" while the `grade_test` run is followed, `AttemptSubmitFlow`). A failed hand-in keeps the answers and offers "Hand in my test".
- A **Review answers** link on the quick check result opens the review endpoint, with correct answers and explanations.

### `LessonViewer`

`LessonViewer` loads `GET /lessons/{id}/document` and shows the lesson as a **notebook** (`LessonBook`, state in `lib/lesson-book.ts`): the sandboxed iframe sits on paper (`--paper`) with spiral binding, a faint margin line and the edge of a stack of pages. The document shows **one page at a time and has no navigation of its own**: the runtime's `LessonShell` (in `sandbox/src/scope/shell.tsx`, so older lessons work without regenerating) draws only the open page, and the app turns the pages.

- **Toolbar** above the book: eyebrow ("Page 2 of 3 · Core"), the page title, **PDF** (prints the three pages from the structured page content with `LessonPdf`; the test is never included), and a "⋯" menu: **Version history** (earlier versions the repairs and restores kept, each with **Restore**), **View code**, and **Reload this lesson** (asks first through `ConfirmDialog`, then reloads the document and starts a fresh iframe; it does not ask for a repair, the repair limit is the server's).

A new page slides in from the right unless the learner prefers less motion. ← and → turn the page when focus is not in the iframe, a field, a dialog or a menu.

A crash the runtime reports shows an alert under the toolbar; while a repair runs a friendly overlay covers the page ("Fixing a glitch on this page…"), and when it finishes the document is reloaded and the new `code_version` is rendered in the same iframe. When the repair fails or the limit is reached the alert says plainly that something did not work (never the page's own error text) and points to Reload and Versions.

## `sandbox/` runtime (shared with backend validation)

The sandbox is its own package at the repo root, so the browser and the backend's `render_check` run **exactly the same** runtime.

```
sandbox/
  src/runtime.tsx       bootstraps React, receives code and data, reports errors and height
  src/scope/            everything generated code may use (below)
  scripts/check.mjs     esbuild parse + Babel AST security/scope scan (called by the backend)
  scripts/render-check.mjs   Playwright headless render + interaction smoke test (called by the backend)
  dist/runtime.js       built bundle; copied to frontend/public/sandbox/ by `npm run build`
```

### Scope available to generated code

| Name | What |
|---|---|
| `useState`, `useEffect`, `useRef`, `useMemo`, `useCallback`, `useReducer` | React hooks |
| `LESSON` | Injected data: `pages`, `final_test` (always empty: the test is its own screen), `media` (id → signed URL, alt, caption, attribution) |
| `Mafs`, `Coordinates`, `Plot`, `Point`, `Line`, `Vector`, `Circle`, `Polygon`, `Text`, `useMovablePoint` | Interactive math graphs ([mafs](https://mafs.dev)) |
| `motion`, `AnimatePresence` | Animations (motion / framer-motion) |
| `Math`, `BlockMath` | KaTeX formula rendering |
| `CodeBlock` | Syntax-highlighted code |
| `Figure` | `<Figure asset="id" />`: renders a `MediaAsset` with caption and attribution. It is the **only** way to show an image or GIF. |
| `Callout`, `KeyPoints`, `PageFrame` | Consistent building blocks for pages |
| `Assessment` | The test UI of lessons made before the test became its own screen (their code still has a `test` page, see `has_embedded_test`). It collects answers and sends them to the parent with `postMessage`. New lessons do not use it. |
| `render` | Mount call, used only by the assembled document |

Adding a library to the scope is a deliberate change. You update `src/scope`, update the allowed identifiers in `check.mjs`, and document it in the prompts for `interactive.generate` and `page.compile`.

### `LessonSandbox`

```tsx
<iframe sandbox="allow-scripts" srcDoc={harnessHtml} />   // no allow-same-origin → opaque origin
```

- The harness sets a CSP: `default-src 'none'; script-src 'unsafe-eval' <runtime>; img-src <api origin>; style-src 'unsafe-inline'`. This means generated code cannot make network requests even if the static scan missed something. (`unsafe-eval` is needed to run the transformed code.)
- The parent posts `{type: "render", code, data, codeVersion, theme}` (media URLs made absolute, because the iframe's origin is opaque) and `{type: "theme", theme}` when the theme changes, which does not restart the lesson. The runtime transforms the TSX with **sucrase** and evaluates it with the scope.
- The runtime posts back `rendered` (with height), `error` (with `phase: transform | runtime`, message, stack, and page), `pages` (`{count, titles}`, when the document starts) and `page_changed` (`{index}`). The parent accepts only messages whose `event.source` is this iframe. The parent sends `render` (with `hide: ["test"]` for a lesson whose `has_embedded_test` is true, so its old test page is left out), `theme` and `set_page {index}`; a freshly started document opens on its first page, so the parent answers `pages` with `set_page` to put the learner back where they were. `test_submit` (from an old lesson's `Assessment`) is still parsed but no longer shown, because that page is hidden.
- **Runtime errors that slipped past `render_check`** trigger `POST /repair`, **once per `code_version`** (`RepairGate`: one crash raises several errors, and one repair covers them; an error from a version the page has moved past is ignored). The server enforces `max_auto_runtime_repairs`: on `repair_limit_reached` the gate stops for good and the learner is told plainly, with **Reload this lesson** and **Version history**. A `stale_code_version` just reloads the document.
- The test is not part of the book: it is taken on its own screen (the Test tab), as many times as the learner likes, each time with new questions; an attempt that is over cannot change (`409 attempt_sealed`).

## Sign in and create account (`/auth`)

A split card: a primary-coloured brand panel (the logo with a marigold mark, a headline per mode, the three steps, tilted translucent cards; on a phone only the logo and headline) beside the form. Segmented tabs switch between "Sign in" and "Create account" without a reload: the address (`?mode=register`, `?next=`) and the tab title follow. The rules and words are in `AuthRules` (`lib/auth-form.ts`, bun-tested): client checks before sending (email shape, a name, the two password rules the server enforces), a live password checklist (the common-password rule is only the server's), friendly messages for a wrong password, the throttle (using `Retry-After`) and a network failure, and where to go afterwards. Server messages stay authoritative and still map onto fields. The password field has a Show/Hide button; the sign-in tab has a **Forgot password?** link. **Create account no longer signs anyone in:** it sends the code and goes to `/auth/verify`. A sign-in the server answers with `verification_required` goes there too (`?purpose=login`).

**Check your email (`/auth/verify`).** The address the code went to is kept in `sessionStorage` (`socra.pendingEmail`, `PendingEmail`) so a refresh still knows it; without it the screen says it lost track and offers **Start again**. One input drawn as six boxes (`autocomplete="one-time-code"`, `inputmode=numeric`): `CodeEntry` keeps only the digits (a pasted `123 456` works) and the code is sent as soon as there are six. A wrong code, whatever was wrong with it, says the same words (`AuthErrors`). **Send a new code** waits a minute (`ResendClock`, using `Retry-After` after a 429); **Use a different email** starts again. The account exists only after the right code; the typed address is shown as typed. Typed calls are in `AuthApi` (`lib/auth-api.ts`).

**Forgot and reset (`/auth/forgot`, `/auth/reset`).** The forgot screen asks for the email and goes to the reset screen **whether or not the address has an account** (the reply is the same), keeping the address in `socra.pendingEmail`. The reset screen says "If <address> has an account, we've sent a 6-digit code to it" (never that it does), takes the code in the same six boxes as the code screen (`components/code-boxes.tsx`) and a new password with the sign-up checklist and Show/Hide, and **Send a new code** waits a minute (`ResendClock`). A weak password shows the server's field message under the password and keeps the code; a wrong code empties the boxes; success signs the person in and goes where they were headed. Rules and words are in `AuthRules` (`validateForgot`, `validateReset`, `resetDescription`, `forgotHref`, `resetHref`).

`?next=` survives onboarding: an incomplete profile goes to `/onboarding?next=<next>`, which finishes to `RedirectPolicy.safeNext(next, "/lessons")`. A signed-in visitor opening `/auth` is sent on by the route guard, and signing out goes to `/`. `sessionStorage` `socra.pendingTopic` is left alone for onboarding.

`/privacy`, `/terms` and `/contact` use the landing page's public header and footer (Privacy · Terms · Contact). The words are not in components: `frontend/content/legal/privacy.md` and `terms.md` are the only copy of the policies (see [legal/README.md](../legal/README.md)), and `content/legal/contact.ts` holds the Contact page's words (the only email address in the product, the five topics with their subject lines, the grievance officer). `LegalDocument` (`lib/legal-document.ts`) reads a markdown file into its "last updated" date, introduction, numbered sections (with anchors) and tables; `LegalPage` lays them out at about 70 characters a line, with a sticky "On this page" list beside the text on a wide screen and folded at the top on a narrow one, and a cookie table that scrolls inside its own box. Editing the copy means editing those files. The Contact page offers "Copy email" (`Clipboard`: the API, then a hidden-box fallback, then the text selected for the learner to copy) and "Open in mail app", and per topic a mail link plus the subject line as text to copy (`Mailto`). The lesson viewer's "⋯" menu has "Report a problem" (the lesson address and page in the message), and `/profile` ends with "Delete my account" (by email for now).

**Time zone at sign-up:** the create-account request also carries the browser's zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`, read by `BrowserTimezone.detect()` and put in the body by `AuthRules.registerBody`). The server keeps it as the learner's zone without starting the 30-day lock, and ignores a name it does not know; a browser that cannot say sends nothing and the learner is on Asia/Kolkata until they choose. The form shows nothing about it.

**Consent at sign-up:** Create account has a required checkbox ("I'm 18 or older, or my parent or guardian has agreed to Socra's Terms of Use and Privacy Policy"). The API refuses a register without `accept_terms` (`400`, "Please confirm to continue.") and keeps `terms_accepted_at` and `terms_version` ("2026-10-25", `User.TERMS_VERSION`) on the user; change the version whenever the Terms or Privacy Policy change in a way that matters.

## Setup (`/onboarding`) and profile (`/profile`)

A focused five-step page (no app navigation): the logo mark, a segmented progress bar and "n / 5", Back (allowed here, unlike in a quiz) and Continue, with each step sliding in from the side the learner came from (no slide for reduced motion). The state is `OnboardingFlow` (`lib/onboarding-flow.ts`, bun-tested): what each step needs, the follow-up questions that fill `grade_or_year` and `field_of_study`, and the profile to save. `OnboardingStore` keeps the place and answers in `sessionStorage` (`socra.onboarding`) so a refresh resumes.

1. **Studies**: School, College, Postgraduate, Working, Self-learner, then a follow-up (class chips; year chips and "What are you studying?"; "What field do you work in?"; an optional focus).
2. **How you learn** (Seeing, Reading, Doing, A mix) · 3. **Goal** · 4. **Language** (each in its own script, English preselected) with optional notes. **Continue on step 4 saves the profile** (`PUT /profile`), so `lc_onboarded` is set before step 5.
5. **Where to start**: chips of what the suggestions are based on (with "Change", back to step 1), four topic cards from `POST /onboarding/topic-suggestions` (`TopicSuggestions`, read defensively; "Show me others" when `has_more`), or "Or type your own topic" (prefilled from `socra.pendingTopic`, which is then cleared). A card and the typed topic are one choice (`TopicPick`). "Start my quick check" creates the lesson; "I'll do this later" goes to `?next` or `/lessons`.

The tiles are friendly copy keyed by the values `GET /profile/options` returns (`OnboardingChoices` merges them: a value only the API knows is shown under its API label). A finished profile visiting `/onboarding` is sent to `/lessons` by the route guard. `/profile` is the same tiles and follow-up questions on one page (`ProfileEditor`) plus the name, the read-only email and the **time zone**. The time zone (`TimezoneField`, phase 10.0) is a box that suggests IANA names as you type (`BrowserTimezone.search`: case, spaces, slashes and underscores do not matter, and a name where a word starts with what you typed comes first), showing the saved zone, else the browser's, else Asia/Kolkata. Its hint says "Your day starts at midnight in this zone. You can change this once every 30 days."; after a change the box is shut and the hint becomes "You can change your time zone again on 5 December 2026." (the date in the learner's zone). A save sends the zone only when it changed or none was saved yet (`BrowserTimezone.payload`), so a first save keeps what the browser said without starting the lock; a name that is not in the list is refused before sending, and the server's `409 timezone_locked` is shown on the field with its date.

**Topic suggestions contract:** `POST /onboarding/topic-suggestions` with the answers of steps 1 to 4 (`education_level`, `goal`, `preferred_language`, `grade_or_year`, `field_of_study`) and `page` (from 0, wrapping) answers `{topics: [{title, title_en, subject, reason}], has_more}`; the cards show `title` (in the learner's language). It follows the backend module `backend/onboarding`, which is still being built: until the endpoint answers, step 5 says it couldn't find ideas and the learner types a topic.

## Design system

All colour, type and radius come from tokens in `frontend/app/globals.css` (Tailwind v4, CSS-first, no `tailwind.config`). Components use token utilities (`bg-primary-soft`, `text-marigold-text`, `shadow-card`), never raw palette classes such as `emerald-600`.

- **Roles.** `primary` (Lagoon teal) is the main action, progress and the current step. `marigold` is the warm partner: secondary calls to action, "waiting for you" states, gaps to learn. `insight` (grape violet) marks AI moments: the learner assessment, the level meter, key-idea callouts and AI feedback. `success` is green and `destructive` is coral.
- **Token family.** Each brand colour has a solid value, a `-soft` tint for backgrounds and a `-text` shade that reads on surfaces (`primary` and `marigold` also have `-deep`, the colour of the pressable marigold button's shadow). The shadcn names (`background`, `card`, `muted`, `border`, `ring`, …) keep working. Light neutrals are teal-tinted (hue 190); dark neutrals are grape-tinted (hue 295). Every token is registered under `@theme inline`, so the Tailwind utility exists.
- **Shape.** `--radius: 1rem`, so inputs and buttons land near 13px (`md`), cards at 22px (`xl`, written `rounded-[22px]`). Cards use a 1.5px border and `shadow-card` instead of a ring.
- **Type.** Fredoka 500/600 for `h1`–`h3` (`--font-heading`, weight 600, line height 1.2, balanced), Nunito 400/600/700/800 for body and controls (`--font-sans`; buttons are 800, labels and badges 700), JetBrains Mono for code (`--font-mono`). All three load through `next/font/google` in the root layout, so nothing is fetched from Google at run time.
- **Solid primary buttons.** The brand teal `--primary` is too light for the label on it (3.06:1; small text needs 4.5:1), so the `default` button fills with a darker family, `--primary-action` (rest), `-hover`, `-pressed` and `-edge` (the flat shadow). Light: 5.13:1, 6.33:1 and 7.52:1 with `--primary-foreground`; dark (the same teal as `--primary`, which already reads on the dark label): 8.80:1, 10.10:1 and 7.60:1. Use these, not `bg-primary`, for any text on a solid teal fill. `--primary` itself is unchanged (progress bars, rings, outlines). `lib/primary-button-contrast.test.ts` fails if a pair drops under 4.5:1 or `Button` stops using them. The same fill carries every other label written in `--primary-foreground`: the header avatar initial, step numbers, the default badge, streak days, answer-letter chips and choice tiles, the sign-in side panel (its step circles are `-action-pressed`, 7.52:1 / 7.60:1) and the landing page's step chips (the third is `insight-text`, 6.85:1 light, 10.65:1 dark, because `insight` itself gives 4.09:1). `bg-primary` stays for fills with no text (progress and level bars, dots, the tab underline, switches) and for the logo's mark, which holds a drawing, not text. The test also fails if a class string puts `text-primary-foreground` on `bg-primary`.
- **Buttons.** `default` (teal, from the tokens above) and `marigold` are pressable: a flat 4px shadow in the `-deep` colour (`-action-edge` for the teal one) that shrinks while the button moves down 3px. `outline` is the same shape on a card surface with a 2px border. Disabled solid buttons turn into a muted surface with no press effect. The press and its transition are off under `prefers-reduced-motion`. `secondary`, `ghost`, `destructive` and `link` stay flat.
- **Badges.** `success`, `marigold`, `insight`, `primary` and `destructive-soft` use the `-soft` and `-text` pair; `default`, `secondary`, `outline` and `destructive` are unchanged.
- **Theme.** `next-themes` toggles the `dark` class; the header's `ThemeToggle` offers Light, Dark and System (the default).
- **The lesson iframe has its own copy.** The page only sends `light` or `dark`, so the palette lives in `sandbox/src/harness.html` as well (run `docker compose run --rm sandbox-build` after editing it). `lib/theme-tokens.test.ts` fails if a colour in the harness differs from `globals.css`, if a brand token is missing, or if a component or sandbox scope file uses a raw palette colour. The harness CSP allows no network fonts, so inside the iframe text uses a rounded system stack (`ui-rounded, "Nunito", system-ui`). Self-hosting Nunito and Fredoka for the iframe would need `font-src` to allow the app origin, or fonts embedded as `data:` URIs.

## `lib/`

- `api.ts`: `ApiClient` and the shared `apiClient` instance. Same-origin credentials, the CSRF header on unsafe methods, one silent refresh on 401 (shared by concurrent requests, never for the auth endpoints), and typed `ApiError`s.
- `types.ts`: mirrors [api.md](api.md).
- `browser-timezone.ts`: `BrowserTimezone`, everything the sign-up form and the profile know about a time zone: `detect`, `initial`, `names` (the engine's list plus the saved and detected zones), `search`, `isValid`, the lock (`isLocked`, `lockNote`, `lockedMessage`) and `payload`. Bun-tested.
- `action-refused.ts`: `ActionRefusedMessage`, the one way to say a refused action. A `403` that is not about the person is a refusal and its own message is shown; since phase 10.0 so is a **`402 insufficient_credits`** (words from the server, else "You need 10 credits for that and have 4."), and `ActionRefusedMessage.refusal(error)` returns `{message, buyPath, required, available}` so a screen can offer **Buy credits** (`buyPath` is `/buy`, built in phase 10.5; nothing returns a `402` before the credit gate is on). The Quick check uses it to show a card with **Get more credits** and **Send my answers**, and `CreditsProvider` adds a toast with a **Buy credits** action for every `402`. `of(error)` still returns just the words, so every screen that used it needed no change.
- `credits/`: the credits screens' logic, as pure classes (`bun test`). `CreditsApi` (typed calls), `CostSizes` (the hints each paid action is quoted with, the same the services send), `QuoteClient` (asks `POST /credits/quote`, remembers 30 s, shares a request between labels, a failure is "no price"), `CostWords` (a price as a learner reads it, including the stages of a lesson from a Quick check), `WalletWords`, `HistoryWords`, `StreakView`, `PlanWords` and `BuyState`, `NoticeDismissals` (hidden for the browser's day), and `ShortDate` (the same "Fri 14 Nov" in every browser). Money is paise on the wire and rupees on screen; **screens never work out a price**.
- `payments/`: the buying screens' logic as pure classes (`bun test`): `PaymentsApi` (typed calls; starting a payment sends an `Idempotency-Key`), `CheckoutAdapters`, `RedirectCheckout` and `RazorpayCheckout` (take a learner through a provider's checkout by what the server returned, never by which provider: a new style is one adapter and one `register`; `checkout-contract.ts` holds the adapter interface, `UnknownCheckout`, `CheckoutUnavailable` and `CheckoutEnd`; Razorpay's on-page window loads its script through `ScriptLoader` only when someone pays, and on completion only navigates to `/buy/return`, never telling the server it was paid; closing the window resolves `closed` and `useBuy` brings the buttons back), `GatewayChoices` (the picker only for two or more), `OneTimeChoices` and `PlanQuantity`, `OrderWatch`, `PaymentWords` (no state name, status code or provider word reaches a learner) and `BuyReturn`. `ApiClient.request` takes optional `headers`. `components/payments/`: `useBuy`, `useOrderWatch`, `GatewayPicker`, `OneTimeCard`, `PlanCard`.
- `components/credits/`: `CreditsProvider` and `useCredits` (the balance for the header, refreshed on page change, focus and every minute, and a toast with **Buy credits** on any `402`), `CostLabel` and `useQuote` (the price beside every button that starts paid work), `BalanceChip`, `NoticesBanner`, `StreakCalendar`, and the small `PageFrame` and `useLoaded` the three pages share. `ApiClient.observe(listener)` tells one place about every failed request.
- **Where a cost is shown (plan §9.2):** the new-lesson form (live, with the stages of a Quick check journey), the mastery choice (each card, and the half-back sentence on the sheets card), the follow-up dialog and card, Try again on a test, Make a lesson on this, Create a lesson for this, the quiz wizard (live as the count, source and level choice change), Try again on a quiz, Add a cheat sheet / revision sheet / both, and the Retry card (`GET /credits/retry-quote`).
- `theme-tokens.test.ts`: keeps the app palette and the sandbox harness palette identical (see Design system).
- `useRunEvents(runId)`: `EventSource` wrapper. It rebuilds state from `snapshot` and closes on terminal events.
