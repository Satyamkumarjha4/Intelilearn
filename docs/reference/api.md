# API reference

Base path: `/api` (Django; port 8000 inside its container, `BACKEND_PORT` on the host). A Next.js route handler proxies `/api/*` to Django, so the browser only calls same-origin `/api/...`.

## Conventions

- **Interactive docs**: Swagger UI at `/api/docs`, ReDoc at `/api/redoc`, OpenAPI 3 schema at `/api/schema` (drf-spectacular; assets are served locally through the sidecar package). Every endpoint is annotated with `@extend_schema` (tags, request and response serializers, error responses), so Swagger is the source of truth for request and response shapes.
- **Paths have no trailing slash.**
- **System**: `GET /api/health` returns database, Redis, and Celery worker status (`200` ok, `503` degraded).

- JSON with `snake_case` fields.
- **Auth**: simplejwt tokens in httpOnly, `SameSite=Lax` cookies set by the API. JavaScript never sees a token. Cookies are used because `EventSource` can't send headers.

  | Cookie | Contents | Path | Lifetime |
  |---|---|---|---|
  | `lc_access` | access JWT | `/` | `JWT_ACCESS_MINUTES` (30) |
  | `lc_refresh` | refresh JWT, rotated on every refresh, with the old one blacklisted | `/api/auth` | `JWT_REFRESH_DAYS` (7) |
  | `lc_session` | `1`: the "signed in" marker for the Next.js route guard | `/` | refresh lifetime |
  | `lc_onboarded` | `1` once the profile is complete (route-guard marker) | `/` | refresh lifetime |
  | `lc_oauth` | signed `state`, `nonce`, PKCE verifier and `next` of a sign-in with a provider; carries no authority (phase 11.3) | `/api/auth/oauth` | `OAUTH_STATE_MINUTES` (10); cleared after the callback |
  | `lc_finish` | a verified provider identity waiting for the "one last step"; carries no authority | `/api/auth/oauth` | `OAUTH_FINISH_MINUTES` (15); cleared when the account is made |
  | `lc_signup` | the **signup ticket**: the signed id of this browser's pending sign-up; `POST /auth/verify` for a sign-up needs it (plan T19) | `/api/auth` | `SIGNUP_TICKET_MINUTES` (1440, the pending row's life); cleared when the account is made |

  `CookieJWTAuthentication` accepts `Authorization: Bearer <access>` first, which is useful for scripts and needs no CSRF, and falls back to the `lc_access` cookie. The markers carry no authority. `Secure` is set when `AUTH_COOKIE_SECURE=true`.
- **Rate limits**:
  - `auth`: register and login, per client address (`AUTH_THROTTLE_RATE`, default `20/min`)
  - `auth_account`: login attempts per email address, whatever the client (`AUTH_ACCOUNT_THROTTLE_RATE`, `10/min`)
  - `auth_refresh`: token refresh, per client (`AUTH_REFRESH_THROTTLE_RATE`, `60/min`)
  - sign-in codes, keyed by the email **as the input says it** (its canonical form, whether or not an account has it), spent only by a request that passed validation: `auth_code_cooldown` (a new code, `1/min` per email), `auth_code_send_email` (`5/hour`), `auth_code_send_ip` (`20/hour` per address), `auth_code_check_email` (`15/hour`), `auth_code_check_ip` (`60/hour`); variables `AUTH_CODE_*_RATE`. Over the limit: `429` with `Retry-After`
  - `auth_oauth`: the three sign-in-with-a-provider endpoints and the last step, per client address (`AUTH_OAUTH_RATE`, `30/min`)

  The client address is what the Next.js `/api` proxy forwards in `X-Forwarded-For` (`TRUSTED_PROXY_COUNT=1` on the Django side). **How Next fills the header (measured on the real stack, phase 11.0):** Next sets it from the socket **only when the client sent none**, so a client's own value is kept and an edge proxy that appends leaves the client's value first. The proxy therefore forwards the **last** entry (`ClientAddress`, `frontend/lib/client-address.ts`), or the Nth from the right when `EDGE_PROXY_HOPS=N` proxies sit in front of Next, never the first. Result: behind an edge that **appends or overwrites**, the address a limit counts is the edge's, whatever the client sends (a forged first entry beside a fixed last one was never limited before the change, and is limited after it). **What is not fixed:** with **nothing in front of Next**, a client that sends a single `X-Forwarded-For` still chooses its own address, and nothing in the app can tell it from the real one. So a deployment needs an edge proxy (it is needed for TLS anyway) that overwrites the header or appends to it; `manage.py check --deploy` fails (`core.E002`) until `TRUSTED_PROXY_COUNT` is set on purpose. The per-account login limit, and the per-user limits below (`lesson_create`, `test_submit`, `topic_suggestions`, `console`), count by account and are not affected. Keeping the API port bound to localhost stops direct requests with a forged header, but not requests through the proxy. **Check it after every deploy:** `make probe-proxy URL=https://<the public site>` (`manage.py probe_forwarded_header`) sends a single forged entry and a forged-first pair through the real front door, reads the throttle cache, and fails if the entry the client chose was the one counted.
- **CSRF**: unsafe methods send `X-CSRFToken`, taken from the `csrftoken` cookie (`GET /auth/csrf` sets it). This is enforced for every cookie-authenticated request and for the auth endpoints; Swagger UI adds the header automatically.
- **Idempotency**: `POST /lessons`, `POST /lessons/{id}/materials`, `POST /quick-quizzes`, its retake (`POST /quick-quizzes/{id}/attempts`) and `POST /quick-quizzes/{id}/create-lesson` accept an optional `Idempotency-Key` header (1 to 128 printable characters without spaces; otherwise `400 invalid_idempotency_key`). A repeat of the same request by the same learner, with the same key and body, within `IDEMPOTENCY_TTL_S` (24 hours) returns the first `2xx` answer with `Idempotent-Replayed: true` and starts nothing. A repeat while the first is still being handled is `409 request_in_progress`. Only successful answers are kept, so a failed request can be repeated with the same key.
- **Refused actions**: an action that starts paid work asks the action gate first (`ACTION_GATE`, see [design.md](../architecture/design.md#418-lessons-the-action-gate-phase-9-metering-seam)). The default gate is the credit gate (since phase 10.9); `OpenGate`, which allows everything and returns no refusal, is for a stack where credits are off and what the tests run on. A gate that says no raises `ActionRefused`, which is the usual `{detail, code}` body: `403` for a refusal with its own `code`, and the credit gate's own: **`402 insufficient_credits`** (the learner has too few credits; `required` and `available` are whole credits, the way `409 already_exists` carries `lesson_id`), **`503 price_unavailable`** (the price table has no live row for something the action is made of: it is never free) and **`409 action_in_progress`** (the same work already holds its credits). A refusal happens before anything is created, so it is safe to ask again. The frontend treats `403` and `402` as refusals and, for a `402`, offers the way to buy more (`ActionRefusedMessage`). It is possible on `POST /lessons`, `POST /lessons/{id}/quizzes/diagnostic/attempt` (nothing is stored, so the answers can be sent again), `POST /lessons/{id}/choice`, `POST /lessons/{id}/materials`, `POST /lessons/{id}/followups`, `POST /lessons/{id}/retry` (the lesson stays failed), `POST /lessons/{id}/test/attempts` (a retake), `POST /quick-quizzes` and the retake `POST /quick-quizzes/{id}/attempts` (nothing is created).
- **Ownership**: every lesson-scoped route returns `404` unless `lesson.owner == request.user`. A malformed id is also a `404`.
- **Rate limit** `console`: the staff-only console API, per staff member (`CONSOLE_THROTTLE_RATE`, `120/min`). A refused `404` does not use it up.
- **Rate limit** `lesson_create`: starting lessons, per user (`LESSON_CREATE_THROTTLE_RATE`, `30/hour`), because each lesson costs model calls.
- **Rate limit** `payment_order`: starting a payment (`POST /payments/orders`), per user (`PAYMENT_ORDER_THROTTLE_RATE`, `10/hour`); `payment_status`: reading an order, per user (`PAYMENT_STATUS_THROTTLE_RATE`, `60/min`); `payment_webhook`: the provider's callback, per client address (`PAYMENT_WEBHOOK_THROTTLE_RATE`, `600/min`; a provider's addresses are not allow-listed, the signature is the control).
- **Rate limit** `credits_quote`: `POST /credits/quote` and `GET /credits/retry-quote`, per user (`CREDITS_QUOTE_THROTTLE_RATE`, `120/min`). `credits_balance`: `GET /credits/balance` and `GET /credits/notices`, per user (`CREDITS_BALANCE_THROTTLE_RATE`, `240/min`).
- **Rate limit** `quiz_create`: making a quick quiz, and starting a retake of one, per user (`QUIZ_CREATE_THROTTLE_RATE`, `30/hour`), because each costs a generation. `topic_traits`: the cheap topic judgement of the quiz wizard, per user (`TOPIC_TRAITS_THROTTLE_RATE`, `60/min`). A quiz has no daily cap on retakes either (retired in 10.9).
- **Rate limit** `test_attempt`: starting an attempt, per user (`TEST_ATTEMPT_THROTTLE_RATE`, `30/hour`), because a retake costs a generation. There is no daily cap on retakes (`retakes_per_day` was retired in 10.9, T33); what limits them is this hourly throttle, the one open attempt a lesson or quiz can have (a start while one is open returns it), and, with credits on, what a retake costs.
- **Console errors** (`code`): `404 not_found` for anyone who is not staff (signed in or not) and for a missing target, `409 not_retryable` · `model_in_use` (carries `nodes`) · and the lesson errors `wrong_stage` · `run_in_progress` · `run_ended` for retry and cancel.
- **Time zone errors** (`code`): `409 timezone_locked` (carries `locked_until`, an ISO instant), `400 invalid` with `fields.timezone`.
- **Plan errors** (`code`), for the purchases of phase 10.6 and the admin today: `400 invalid_plan`, `400 invalid_amount`, `409 queue_full` (carries `open_periods` and `limit`).
- **Streak errors** (`code`): `409 nothing_to_repair`, `409 repair_limit`, and `402 insufficient_credits` for a repair the learner cannot pay for.
- **Lesson errors** (`code`): `400 invalid_answers` · `sheets_only`, `404 not_found`, `409 wrong_stage` · `already_attempted` · `attempt_sealed` · `locked` · `not_failed` · `not_attempted` · `run_in_progress` · `run_ended`, `503 llm_not_configured` (no model is bound for the first step) · `queue_unavailable` (the broker is down; the lesson is failed so Retry works later).
- **Errors**: `{"detail": "...", "code": "...", "fields": {...}}`; a few carry more for the client to act on (a follow-up's `already_exists` adds `lesson_id`, and a sheet's adds `kinds`).
- **Pagination**: cursor-based, `?cursor=&page_size=20` → `{results, next, previous}`.

## Auth and profile

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/auth/csrf` | none | `204`, sets `csrftoken` |
| POST | `/auth/register` | `{email, password, name, accept_terms, timezone?}` (`accept_terms` must be `true`: the person is 18 or older, or a parent or guardian agreed to the Terms of Use and Privacy Policy; `timezone` is the browser's IANA zone, a blank or unknown name is ignored) | **`202 {status: "verification_required"}`** and the `lc_signup` ticket cookie. **No account, no session, no credits yet:** a pending sign-up is kept and a 6-digit code is emailed to the address as typed. The reply is **the same for an address that already has an account** (status, body, cookie; its owner is emailed a notice instead). `400` with `fields` for a malformed or disposable address, a weak password or a missing confirmation (never "already exists"); `429` |
| POST | `/auth/verify` | `{email, code, purpose: "signup" \| "login"}`; for `signup` the `lc_signup` cookie must come with it and match the live pending sign-up | `200 {user}`, sets the session cookies and clears the ticket. For `signup` this **creates the account** (email as typed, verified by code, profile, the zone, the terms, one `account_ready` and so the 30 credits); for `login` it verifies an existing account. **`400 invalid_code` for every failure** (a wrong, expired, used or killed code, a missing, forged or stale ticket, an unknown email, a locked email, a body that does not parse); `429` |
| POST | `/auth/verify/resend` | `{email, purpose}` | `202 {status: "sent"}` **always**. A `signup` resend needs the ticket and sends nothing without it (so a stranger cannot cancel someone's live code); a `login` resend sends only to an active unverified account. A new code cancels the old; `429` with `Retry-After` |
| POST | `/auth/password/forgot` | `{email}` | `202 {status: "sent"}` **always**, whether or not the address has an account. A 6-digit reset code is mailed **only** to an active account that can use one; an account that signs in with Google and has no password is mailed "sign in with Google" instead; an unknown address, a closed account and an address that has **only a pending sign-up** get nothing and the same reply. A new code cancels the old; `429` with `Retry-After` (the same limits and keys as `/auth/verify/resend`); `400` for a malformed address |
| POST | `/auth/password/reset` | `{email, code, new_password}` | `200 {user}` and the session cookies: sets the password, **blacklists every refresh token of the account**, counts the reset as proof of the inbox (a legacy, staff-vouched or never-verified account becomes `code`-verified, and an account that was never announced gets its signup credits) and signs the person in. An account with no usable password and no linked sign-in (one staff approved) gets its **first** password. **`400 invalid_code` for every failure of the code** (the same words as `/auth/verify`); a weak password is `400` with `fields.new_password` (judged against the typed address only, so the answer is the same for every address) and **spends no try**; `429` |
| GET | `/auth/captcha` | none | `{enabled, site_key}`: whether the sign-up check (Cloudflare Turnstile) is on, and the public key its widget needs (`""` while off). **While it is on, `POST /auth/register` and `POST /auth/verify/resend` need `captcha_token` (the widget's answer) and answer `400 captcha_failed` for a missing or failed one, before anything is sent or kept** (a failure is counted for the abuse board). While it is off the field is ignored. Only those two endpoints are challenged: `password/forgot` is not (it sends nothing to an address without an account). A challenge that cannot be checked (the network, a bad answer) is a failure: it fails closed. `public_pages` throttle |
| GET | `/auth/providers` | none | `{providers: [{key, label}]}`: the sign-in providers that are on (`AUTH_PROVIDERS_ENABLED`; the stand-in `fake` also needs `AUTH_ALLOW_FAKE_PROVIDER`), so a screen never draws a dead button. Public, `public_pages` throttle |
| GET | `/auth/oauth/{provider}/start?next=` | none (a browser navigation) | `302` to the provider with `state`, `nonce` and a PKCE `S256` challenge, and the signed `lc_oauth` cookie. `next` goes through `RedirectPolicy` (a path on this site or dropped). A provider that is off: `302 /auth?error=provider_off`, no cookie. `auth_oauth` throttle (`AUTH_OAUTH_RATE`, `30/min` per address) |
| GET | `/auth/oauth/{provider}/callback` | the provider's `code` and `state` (and `error`) | `302` to `/auth[?next=]` with the **session cookies** (signed in: a link to an account whose email its owner proved, or a take-over of one nobody proved, see below), to `/auth/finish[?next=]` with the **`lc_finish`** cookie (a new person: **nothing is created yet, so no account and no credits**), or to **`/auth?error=<code>`**: `email_not_verified` (the provider does not call the email verified: only the boolean `true` or the exact string `"true"` counts), `provider_off`, `state_mismatch` (a wrong, missing, replayed or other-provider state), `sign_in_failed` (the person said no, the exchange or the token check failed, a **staff account**, or an address linked to a different person of that provider), `account_closed`. `lc_oauth` is cleared every time. A **take-over** (an account whose email was never proved: unverified, `legacy`, `staff` or `operator`) makes its password unusable, blacklists every refresh token, marks it verified by the provider and links the identity; an account whose email the owner proved is only **linked**: no second account and no second grant |
| GET | `/auth/oauth/finish` | none (the `lc_finish` cookie) | `200 {email, name}` for the form; `404` with no live ticket |
| POST | `/auth/oauth/finish` | `{name, accept_terms, timezone?}` (`accept_terms` must be `true`; the zone is the browser's) | `201 {user}` and the session cookies: **creates the account** (no password; email as the provider gave it; verified by the provider; terms stamped; identity linked; the zone applied; a pending code sign-up for the same address deleted), gives the 30 credits once, clears `lc_finish`. `400` with `fields` for a missing name or confirmation; `400 finish_expired` with no live ticket. If the person already has an account by now it signs that one in and makes no second |
| POST | `/auth/login` | `{email, password}` (any case or alias of the address finds the account: the lookup is by canonical email) | `200 {user}`, sets cookies; `401 invalid_credentials`; **`403 verification_required`** when the password is right but the email was never proved (a login code was emailed; enter it at `/auth/verify` with `purpose: login`; no cookies) |
| POST | `/auth/refresh` | none (uses `lc_refresh`) | `200 {user}`, rotates cookies; `401 session_expired` clears them |
| POST | `/auth/logout` | none | `204`, clears and blacklists |
| GET | `/auth/me` | none | `{id, email, name, profile_complete, is_staff}`, or `401`. `is_staff` says whether the person may use the [console](#console-staff-only) (the same user object is returned by login, register and refresh) |
| GET | `/profile` | none | `Profile`, including `timezone` (the learner's IANA zone, `""` until set), `effective_timezone` (the zone in force: `timezone`, or `Asia/Kolkata`) and `timezone_locked_until` (when the zone can next be changed, or `null` when it can be changed now) |
| PUT | `/profile` | `Profile` fields; `education_level`, `learning_preference`, `goal` required | `200 Profile`, sets or clears `lc_onboarded` |
| PATCH | `/profile` | any subset (including `name` and `timezone`) | `200 Profile`. `timezone` must be a name in the zone database (`400` naming `timezone` otherwise; blank is refused too). The first value set is free; a later change is allowed once every 30 days: inside the 30 days, `409 timezone_locked {detail, code, locked_until}` and nothing in the request is saved. Sending the zone already saved is not a change. `PUT` takes `timezone` the same way and leaves it alone when it is left out |
| GET | `/profile/options` | none (no sign-in) | `{education_level, learning_preference, goal, preferred_language}`: each a list of `{value, label}` in display order, exactly what the profile accepts. The screens read their choices from here (a language outside the list, or notes over 2000 characters, is a `400`) |

### Follow-up lessons

| Method | Path | Body | Response |
|---|---|---|---|
| POST | `/lessons/{id}/followups` | `{level: "foundation" \| "advanced"}`; optional `Idempotency-Key` header | `202 {lesson_id, run_id}`: a lesson of its own made from a **ready** lesson of the caller's, once for each level. Its topic is `Foundations of X` or `Advanced X` (a suffix, `(2)`, when another of the learner's lessons has that name; it is never linked to one that exists), its level is fixed by what it is for (Foundation: Beginner, Advanced: Expert), it has `entry` and `origin` `followup`, no quick check and no rating, **the parent's note** (`user_context`) but none of its concepts, and a Beginner's prerequisites are planned as usual. It counts against the new-lesson rate limit and asks the action gate for `lesson.followup` (hint `followup_level`). `409 already_exists {detail, code, lesson_id}` when that level was made (the client opens that lesson; nothing is asked or made), `409 wrong_stage` unless the parent is `ready`, `400` for a missing or unknown `level`, `400 sheets_only` for a lesson that is only study sheets (it has no test to follow up on), `404` for another learner's lesson, `503 llm_not_configured` when the lesson planner (and, for Foundation, the prerequisite planner) has no model, `429`. `POST /lessons` still refuses `origin: followup`. |

**The offer** on a graded attempt (`followup`, in the attempt and in the submit answer): `{kind, action, lesson_id}`, decided by the server (spec 3.3). `kind` is `foundation`, `advanced` or `inline_suggestion`. `action` is `generate` (make that lesson), `revisit` (a Foundation lesson that exists, in `lesson_id`), `open` (an Advanced lesson that exists) or `revisit_or_related` (the quiet note for a learner who rated themselves low and failed). A Fail gets the Foundation offer until the learner has passed once (a score at or above the lesson's Fail line on an earlier graded attempt), except from a learner who rated themselves low (only the note) and an attempt of blank answers (nothing); an Excellent gets the Advanced offer on every such attempt except from a learner who rated themselves high (nothing). A learner's category comes from their stars, or from the level of their lesson (a Foundation follow-up is a Beginner lesson and an Advanced one an Expert lesson, so chains of follow-ups stop on their own).

## Payments

Buying credits. All but the webhook need a signed-in learner and are owner-scoped. **Credits are granted only from a signature-verified callback from the provider (or the server asking the provider itself); the page the browser returns to grants nothing.** Money is paise (100 paise = 1 rupee, tax included) and the currency is INR. Which providers exist is the environment's: `PAYMENT_GATEWAYS_ENABLED`, `PAYMENT_DEFAULT_GATEWAY`; the fake gateway (`fake`) exists only where `PAYMENT_ALLOW_FAKE_GATEWAY` is true. Plan: [credits-implementation-plan.md](../archive/credits-implementation-plan.md) §8.2.

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/payments/gateways` | none | `{gateways: [{key, display_name}], default: key \| null}`: the ways to pay that are switched on, in order, and the default. Empty (and `default` null) when buying is not open. The buy page asks which to use only when there are two or more |
| POST | `/payments/orders` | `{plan, quantity?, credits?, gateway?}`: `plan` is `one_time`, `weekly_pro`, `monthly_pro` or `pro_plus`; `quantity` is the weeks of Weekly Pro (default 1); `credits` is the amount of `one_time`; `gateway` one of the enabled ones, else the default. **No price is read from the client.** Optional `Idempotency-Key`. Throttle `payment_order` | `201 {id, status, gateway, plan: {key, name}, quantity, credits, amount_paise, currency, refunded_paise, created_at, fulfilled_at, checkout}`. `credits` is what the order gives (the bought amount, or a plan's credits in all). `checkout` says how to pay: `{kind: "redirect", redirect_url}` (go there) or `{kind: "client", adapter, client}` (the provider's on-page checkout, opened by the named adapter with these non-secret parameters). | GET | `/payments/orders/{id}` | none | One order, for the page the learner returns to. `status` is `created`, `pending`, `paid`, `fulfilled`, `failed` or `expired`; `fulfilled` is when the credits are in the wallet. **It never grants by itself:** if the order is still waiting after 30 seconds the server asks the provider (the same answer the five-minute job reads), and credits arrive only from that or from a signed callback. Another learner's order is a `404`. Throttle `payment_status` |
| POST | `/payments/webhooks/{gateway}` | the provider's raw body | The provider's callback. **No sign-in and no CSRF cookie: the only view with neither.** The raw body is read (so the proxy must not change it), capped at 256 KB (`413 body_too_large`), and its signature is verified **before any database work** (`400 invalid_webhook`); `404` for a gateway that does not exist or is not on. `200 {received}` for an applied, repeated or ignored event, including one for an order we do not know and one whose amount does not match (recorded, nothing granted): the provider must not retry those forever. Throttle `payment_webhook`, per client address |

**What an event does** (one transaction with its row; each event id takes effect once): *succeeded* makes the order paid and fulfils it (a late success after the order expired or failed still grants: the money was taken), *failed* ends a waiting order, *refunded* and *disputed* take back the refunded share of the purchase's credits (unstarted weeks first, then what is left of its buckets, never below zero; what was already spent is recorded as the shortfall) and add to `refunded_paise` without changing the order's state. An amount or currency that does not match the order is recorded as `amount_mismatch` and changes nothing.

**Stripe** (`gateway` = `stripe`, `POST /api/payments/webhooks/stripe`; send it through the frontend's address). The signature is `Stripe-Signature: t=…,v1=…` (HMAC-SHA256 of `t.body` with `STRIPE_WEBHOOK_SECRET`, any one `v1`, within five minutes: a bad or old one is `400 invalid_webhook`). Events it acts on, and what each becomes: `checkout.session.completed` (paid) and `checkout.session.async_payment_succeeded` → *succeeded*; `checkout.session.async_payment_failed` and `checkout.session.expired` → *failed*; `refund.created` and `refund.updated` (succeeded refunds only) → *refunded*, the refund's own amount under the event id `refund:<refund id>`; `charge.dispute.created` → *disputed*. `charge.refunded` is deliberately ignored (it carries the charge's running total). Any other event is answered `200` and ignored. A refund or a dispute finds its order by the payment intent the order kept when it was paid. The buyer is sent to Stripe's own page (`checkout.kind` is `redirect`); the order's `provider_ref` is the Checkout Session id (`cs_…`) and `payment_ref` the payment intent (`pi_…`).

**Razorpay** (`gateway` = `razorpay`, `POST /api/payments/webhooks/razorpay`; through the frontend's address too). The signature is `X-Razorpay-Signature`: the hex HMAC-SHA256 of the raw body with `RAZORPAY_WEBHOOK_SECRET` (the webhook secret, not the API key secret); a bad one is `400 invalid_webhook`. Razorpay signs **no timestamp**, so replay is stopped by `X-Razorpay-Event-Id`, which is the event's id and applies once; a signed event that needs it and has none is `400`. Events it acts on: `order.paid` (when the order is paid) → *succeeded*; `payment.failed` → one failed attempt (recorded; the order stays open, since the checkout window offers a retry); `refund.created` and `refund.processed` (processed refunds only) → *refunded*, the refund's own amount under the event id `refund:<refund id>`; `payment.dispute.created` → *disputed*. `payment.captured`, `payment.authorized` and every other event are answered `200` and ignored. A refund or a dispute finds its order by the payment (`pay_…`) the order kept when it was paid. The browser gets a **client** checkout: `checkout` is `{kind: "client", adapter: "razorpay", client: {key, order_id, amount, currency, name, description, prefill?, retry: {enabled: true}}}`, all public (the key id, never the secret); the order's `provider_ref` is Razorpay's order id (`order_…`).

## Console (staff only)

The API behind the staff console (`backend/console/`; `tag: console` in Swagger). Everything is under `/api/console/`.

- **Access**: `User.is_staff` only (`IsAdminUser`). Anyone else, signed in or not, gets the same `404 not_found` as a page that does not exist, on reads and writes alike, so the area does not announce itself. An invalid or expired token is still a `401`, so the silent refresh runs; but an access cookie that has just expired makes the request anonymous, which is a `404` here, so the frontend client (`ConsoleApi`) renews the session and tries a 404 once more. Cookie auth and CSRF are the usual ones. `120/min` per staff member. Responses are `Cache-Control: no-store`.
- **Secrets**: a provider is the *name* of its key's environment variable and `api_key_set` (whether it is set); a key's value is never returned, logged or audited.
- **Formats**: model cost is a USD decimal string with six places (`"0.012345"`), money in the credit and payment endpoints is integer paise or a rupee decimal string (`"350.00"`), times are ISO 8601, lists of rows (`runs`, `providers`, `models`, `learners`, `audit`, `payments`) use the usual cursor pagination (`?cursor=&page_size=`, `{results, next, previous}`), and errors have the usual `{detail, code, fields?}` shape.
- **Ranges** (`?range=`): `today` (since midnight UTC), `7d` (today and the six days before) and `30d`, each ending now. `GET /console/usage` and its CSV also take `range=custom` with `start` and `end` (dates, `YYYY-MM-DD`; whole days, both included, at most 366 days, in order), and default to `7d`. The *previous* period is the same length, ending where the range starts.
- **Calls**: a model call is one *attempt* (a retry, or the next model of the chain, is another call). It is `ok` (worked on attempt 1), `retried` (worked on attempt 2 or later) or `failed` (any other status), so the three add up to the calls made. A *fallback* is an attempt on the second or later model of a step's chain (`fallback_index` above 0) and a *retry attempt* one with `attempt` above 1, whatever came of them. Call times are of the calls that worked, as interpolated percentiles (Postgres `percentile_cont`). Rate-limit waits are part of `latency_ms`; `rate_limit_wait_ms` says how much.
- **Audit**: every request that changes something writes one `AuditEntry` (actor, action, target, before, after) in the same transaction as the change; refused requests and reads write none.

**The run timeline** (`timeline` of `GET /console/runs/{id}`): `[{node, phase, start_offset_s, duration_s, state}]`, oldest start first, from what `GraphRunRecorder` keeps on the run as it streams (`node_status` and `node_timings`: when each graph node first started, when it last finished, and how often the graph ran it again). `start_offset_s` is seconds after the run started (never negative); `duration_s` runs from the step's first start to its last finish, or to now while it is still running. `state` is `failed` (the step failed, or was skipped after failing), `waiting` (a paused run is waiting in this step for the learner, so it has no duration), `retried` (the graph ran the step again after its output failed a check) or `ran`. `phase` (`diagnose`, `author`, `build`, `post`, `other`) comes from the code module that defines the node. Model-level retries and fallbacks are not steps: they are in `model_calls` (`attempt`, `fallback_index`). A run from before timings were kept lists its steps from `node_status` with `start_offset_s` and `duration_s` null.
